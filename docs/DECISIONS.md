The rest were found empirically, which is also why the spec keeps a real envelope verbatim rather than a fabricated one: it is evidence of a shape wavebird has not published and could change. `fields` is read tolerantly (ignored unless an Array), consistent with every other tolerant read in the gem — an unexpected shape must not turn a reportable API error into a `NoMethodError` inside the reporter. **`#diagnostic_message`, and deliberately *not* `#detailed_message`.** The obvious name is taken: Ruby 3.2+ defines `Exception#detailed_message(highlight:)` and calls it while rendering an uncaught exception. The first version of this change overrode it with a zero-arity method, so a `Wavebird::Error` reaching the top level raised `ArgumentError` **inside Ruby's error printing**, replacing the real failure with a confusing one. Verified on 3.4.10, renamed, and pinned by a spec that calls `detailed_message(highlight: false)` so the name cannot be reclaimed. **Both fail-silent reporters now log the diagnostic form**, since `on_error` and the log are where a human actually meets the error. `Client#report_swallowed_error` keeps an `is_a?(Error)` guard because a raising `before_send_text` hook (#028) sends it a plain exception; `Facade#report` does not, because every caller rescues `Error` specifically — a defensive branch there would be untestable and therefore untested. **Context worth keeping:** the investigation that produced this also established that the gem's request body is correct. The same envelope's `allowed_top_level_fields` — `client_id, session_id, job_type, locale, slots_requested, prompt, slot_hint, overrides, consent` — matches exactly what `create_placement` sends, and wavebird's own dashboard quickstart body was rejected identically against the same project, so the remaining failure is that project's configuration rather than anything in this gem.
