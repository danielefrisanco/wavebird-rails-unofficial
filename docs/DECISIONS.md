# Decision log — wavebird-rails

Numbered, newest last. Every deviation from the upstream TS SDK, and every
TS↔Rails mismatch, gets an entry: context → options → decision → rationale.
Decisions that go against the original SDK require Daniele's approval first
(see WAY_OF_WORK.md).

| # | Date | Status | Decision |
|---|------|--------|----------|
| 001 | 2026-07-18 | approved | Async decision delivery via ActiveJob poll + Turbo Stream broadcast instead of porting `getDecisionViaWebSocket`. Rationale (verified in `wavebird-client.ts`): upstream's WS is per-decision and short-lived (ticket POST → open WS → wait for one message → close), with polling as its own trusted fallback — so a held long-poll `GET /v1/decisions/{slot_id}?wait_ms=` delivers equivalent push latency without a Ruby WS dependency. Browser↔Rails stays WebSocket via ActionCable/Turbo Streams. **Deferred todo:** implement the Rails↔wavebird WS transport behind the same interface in a later version (or if wavebird adds a persistent multi-slot channel). Poller must mirror upstream deadline semantics (`timing.ts`/`clamp.ts`, `decisionTimeoutMs`, long-poll attempt counts). Approved by Daniele. |
| 002 | 2026-07-18 | approved | `reportGeneration()` exists in the TS SDK but not in the build prompt — port or skip? Investigated: canonical route `POST /v1/jobs/{job_id}/generation/{event}`, events `started\|finished\|failed`, body `generation_id`/`model_id`/`usage_json`/`error`, fire-and-forget. **Approved by Daniele: port in v1.** |
| 003 | 2026-07-18 | approved | **Error posture conflict** — TS SDK public methods never throw (fail-silent + `onError` observer); build prompt §3.9 demands typed exceptions per HTTP error code. **Approved by Daniele: layered** — low-level `Wavebird::Client` raises typed errors; Rails-facing facade is fail-silent like upstream. |
| 004 | 2026-07-18 | approved | `decisionDelivery: "callback"` mode (wavebird POSTs decision to a `callback_url`) — not in build prompt; an engine-mounted callback route would fit Rails well. **Approved by Daniele: later todo** — design client so it can slot in post-v1 without breaking changes. |
| 005 | 2026-07-24 | approved | **Local enum validation on `#record_beacon` / `#record_consent`** (build prompt §4.4/§4.5) — upstream does *not* validate: `mapSdkBeaconTypeToCanonicalEvent` returns `null` for an unknown `beacon_type` and `sendBeacon` then falls back to the legacy wrapper endpoint (`/public/wrapper/v1/beacons`), which this canonical-only client deliberately does not mirror. With no fallback route available, an unmapped event has nowhere to go, so the gem rejects it locally with `ArgumentError` *before* the request is built — failing fast instead of round-tripping a server 400, and keeping the `asset_token` off the wire on a typo. `#record_consent` validates `decision`/`source` against the canonical enums after alias canonicalization. Same posture as the already-ported `report_generation` event check. Upstream has no `/v1/consent` client method at all, so nothing was superseded there. Approved by Daniele. |
| 006 | 2026-07-26 | approved | **Slot markup: plain `<section>` + Stimulus, not a Turbo Frame.** The plan (Phase 5) said `wavebird_slot` should render a hidden *Turbo Frame*. But the live hosted renderer (`docs/upstream/render-js-snapshot-2026-07-18.js`) *owns* the slot element: it mounts an iframe into it via `target.replaceChildren(...)` and toggles `target.hidden`, reading its POST endpoint from a `data-wavebird-endpoint` attribute — it never consumes a Turbo Frame `src`. A real `<turbo-frame src>` would fight the renderer for the element's lifecycle. The faithful port of the original SDK's frontend contract (and the integration brief's plain-HTML example) is a *plain* element decorated with a Stimulus controller (`data-controller="wavebird"`) — which is also the correct Hotwire primitive for wrapping third-party JS (Stimulus decorates; Turbo Frames fetch/replace). Async mode (Phase 6) reveals/hides this same element via Turbo **Streams**, not a Frame. The "Turbo Frame" wording predated fetching the render.js snapshot. Approved by Daniele. |
| 007 | 2026-07-26 | approved | **Dev/test toolchain: Ruby 3.4 + Rails 8.1.** Phase 5 is the first phase to load the Rails view/controller stack. The resolved `railties 8.1.3` uses Ruby 3.4+ syntax (anonymous rest params), so its `actionview` cannot even parse on the previously-pinned Ruby 3.3.0 — the earlier phases passed only because they never loaded actionview. Daniele updated `ruby-build` and installed **Ruby 3.4.10** (`.ruby-version`); the gem still declares `required_ruby_version >= 3.2` and `railties >= 7.1, < 9` (a consumer on Ruby 3.3 simply resolves an older, compatible Rails). The parity matrix's Rails 7.1/7.2/8.0 targets are unchanged; 8.1 was never a target, it just resolved as "latest < 9". Approved by Daniele. |
| 008 | 2026-07-28 | approved | **Stimulus controller exposes two host entry points, not one — layered "a + c".** The hosted `render.js` exposes exactly one contract (`window.wavebird.withTurn(target, work)`, a framework-agnostic global — upstream's own standard for a vendor-distributed widget) and has no Stimulus/event surface of its own; there was nothing to port for "how does the host hand its chat turn to us." Rather than invent a single Rails-flavored interface, the `wavebird` Stimulus controller supports both: **(c)** the faithful upstream global keeps working untouched — a host that copy-pastes the brief's `window.wavebird.withTurn('#wavebird-slot', work)` needs nothing from us; and **(a)** a Stimulus-idiomatic `wavebird:turn` CustomEvent bridge (`this.dispatch`/`addEventListener` — the blessed Stimulus cross-boundary primitive, vs. the `getControllerForElementAndIdentifier` anti-pattern) wraps `detail.work` in `withTurn`, injecting the stable `session_id` as the explicit `body` (render.js's default body is only a random uuid, so path C alone would not carry our session id). Path A degrades to running `detail.work()` unwrapped when `window.wavebird` is absent. The event bridge is surface beyond upstream, hence this decision. Both paths funnel into the same `withTurn({target: this.element, endpoint, body})` call. Approved by Daniele. |
| 009 | 2026-07-28 | approved | **Async reveal keeps the asset_token server-side by reconstructing frame_url.** In async delivery mode the decision arrives via `GET /v1/decisions/{slot_id}`, which (unlike the blocking `/v1/placements` response) carries the raw `asset_token` and a `creative`, **not** a ready `render.frame_url`. render.js *would* reconstruct `frame_url` from the token in the browser (`renderFrom`), but that puts the `asset_token` on the wire — forbidden by the security posture (secret_key/asset_token never in browser output, build prompt §5). So the **server** reconstructs `frame_url = {api_base_url}/v1/render/{token}` using render.js's own formula (`CGI.escapeURIComponent`, matching the client's `#encode`) and broadcasts only that + dimensions/label — the token never leaves the server, and both paths present an identical browser boundary. The reveal itself calls `window.wavebird.renderPlacement({target, placement:{render}})` (via the Stimulus `signalTargetConnected` handler) — the hosted renderer's own out-of-band entry point, which `startTurn` also uses internally — so the iframe mount + viewability beacons match the blocking path with zero Ruby reimplementation. The shared browser-safe projection is `Wavebird::SlotPayload` (blocking controller + async job). Verified against the render.js snapshot (`renderPlacement`/`renderFrom`/`clearPlacement`). Security-first per Daniele; the "closest to the SDK + broadest/most-useful" framing chose `renderPlacement` over Ruby-rendered iframes. Approved by Daniele. |
| 010 | 2026-07-28 | approved | **Async mode's ActiveJob + Turbo/ActionCable are optional, lazy-loaded — not gem dependencies.** The gem's runtime deps stay minimal (faraday + railties); a client-only or API-only host that never uses async must still `require "wavebird-rails"` cleanly. So `Wavebird::DecisionPollJob` lives under `lib/` (off the engine's Zeitwerk autoload path), is guarded by `return unless defined?(ActiveJob::Base)`, and is lazy-`require`d by the controller only on the async path — which is itself reached only when `Turbo::StreamsChannel` **and** `ActiveJob::Base` are defined. Absent either, the controller logs one warning and falls back to the blocking default (the standard "optional integration / graceful fallback" gem pattern — Devise/Sidekiq/Lograge style). `activejob` is a dev dependency (tests only); async's runtime requirements (ActiveJob + ActionCable adapter) are documented in the README/INSTALL, not forced. `config.async_queue_name` (default `:default`) sets the queue. Approved by Daniele. |
