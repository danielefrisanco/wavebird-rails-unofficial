| 011 | 2026-07-31 | approved | **Boot-time security guards: require-context + asset-path scan, both raising `ConfigurationError`.** Build prompt §4 demands the gem "fail loudly (raise at boot, not silently no-op) if someone requires the client from `app/javascript` or similar", but names no mechanism. | 015 | 2026-08-02 | approved | **Async decision streams are scoped to the session, and the endpoint stops trusting the browser.** Three findings from the Phase 10 security review, all fixed. **(a) Cross-session leak (high).** `SlotHelper#wavebird_slot` named the Turbo Stream `wavebird_slot_{position}` and the endpoint broadcast to the same name, so *every visitor rendering that position shared one channel*. One visitor's decision — including the `frame_url` that embeds their `asset_token` — was broadcast to all of them, mounting their ad in strangers' pages and firing their viewability/render beacons from unrelated browsers, corrupting both the token boundary of #009 and beacon attribution. Fixed by deriving the name from position **and** session id in one place (`SlotPayload.stream_name`), used identically by the helper (which subscribes) and the endpoint (which broadcasts). This restores upstream's scope rather than inventing one: the TS SDK's decision transport is a *per-slot* WebSocket (`createDecisionWsTicket` → open → one message → close), scoped to a single caller by construction; the shared per-position channel was the part we invented. A blank session id degrades to the blocking path in both the helper and the endpoint (neither needs a stream at all), rather than silently producing a shared channel — the helper raised at first, corrected in **#016**. **(b) Client-chosen broadcast target (medium).** The endpoint read `stream_name` straight from request params and passed it to `broadcast_append_to`; Turbo signs stream names on the subscribe side but not the broadcast side, so a scripted client could push its payload onto any stream. `stream_name` is no longer a permitted param, no longer a Stimulus value, and no longer sent in the request body. `DecisionPollJob#perform` takes `position` explicitly instead of parsing it back out of the stream name. **(c) Browser-supplied `overrides`/`consent` beat server config (medium).** `merge_hashes` lets call-site values win over `config.default_*`, which is right for a server-side caller but not for the engine endpoint, where the "caller" is an untrusted page: it could clear `blocked_categories`, zero a `bidfloor`, or claim `semantic_targeting: true` on the user's behalf. Both are now dropped from the permitted params; `overrides` comes from `config.default_overrides` (merged by the client) and consent from a new `config.default_consent`. That option defaults to `nil`, so #013 stands unchanged — the gem still sends no consent object unless the host supplies one; `default_consent` is only the server-side channel for supplying it now that the browser cannot. `slot_hint` is still accepted from the browser: it carries layout sizing the page legitimately knows, and does not steer brand safety or consent. Regression coverage is a two-session Capybara spec; verified against the pre-fix code, where visitor B's page contained visitor A's asset token. Approved by Daniele. |

| 017 | 2026-08-04 | approved | **The browser payload is the wavebird response shape, not a flat projection of it — the gem never rendered an ad with the real renderer.** Found the first time the gem was driven against the live sandbox in a browser. `SlotPayload` returned `{fill: true, frame_url: …, width: …, …}`, but the hosted renderer resolves an endpoint response through two pure functions: `placementFrom(input)` unwraps `input.placement` (or `input.decision.placement`, otherwise the input itself), and `renderFrom(p)` returns a render **only** from `p.render.frame_url`, falling back to rebuilding the URL from `p.asset_token` — which this payload deliberately never carries (#009). A flat `frame_url` satisfies neither branch, so `startTurn`'s own guard (`if(!p||!p.render)`) discarded the response and `renderPlacement` resolved `null`; both call `clearPlacement`. The renderer has **no error path for an unresolvable payload** — an unreadable response and an honest no-fill are the same code path — so the slot silently stayed empty in every mode, blocking and async alike, with nothing in the console. This was our deviation, not upstream's: the integration brief says the backend "returns the wavebird JSON response to the browser", and we returned a reshaped one.
